## Что за проект

**Название:** LifeOS
**Тип:** Операционная система для жизни.

**Суть:** Перенести управление всеми сферами жизни из разрозненных инструментов (Google Sheets, заметки, планировщики) в единую локальную систему с AI-ассистентом.

**Основная концепция:**
Любые данные → AI → Структура → Локальное хранение → Аналитика → Осознанные решения

**Текущий фундамент (что уже есть):**

- Финансовое ядро: Receipt → AI extraction → ReceiptItem → Operation → Financial calculations
- Расширяемая архитектура: любой новый домен (здоровье, привычки, планы) подключается по тому же принципу
- AI-слой для структурирования любых данных
- Система знаний (Memory) с индексацией и семантическим поиском
- Архитектурные решения по категориям, долгам, бюджету и пользовательским полям

## Главные принципы

- **Принцип 1 — Единая структура данных.** Все операции, покупки и расчёты в одной понятной модели.
- **Принцип 2 — AI не владелец данных.** Он только извлекает и структурирует. Изменения в базу — только через Repository.
- **Принцип 3 — Бизнес-логика отделена.** Финансовые понятия → Domain/Financial Rules. Техническая реализация → Architecture/Database.
- **Принцип 4 — Один факт = один источник.** Не дублировать информацию. Если про архитектуру → только `02_Architecture`, про базу → только `05_Database_Specification` и т.д.
- **Принцип 5 — Полная конфиденциальность.** Данные пользователя — это святое. Никакие данные не передаются третьим лицам без явного согласия пользователя. По умолчанию всё хранится локально. Внешние AI-вызовы (OpenRouter) используются только для выполнения конкретной функции (распознавание чеков, создание эмбеддингов) и не сохраняются на стороне провайдера дольше необходимого.
- **Принцип 6 — Бесплатная работающая версия.** Все основные функции приложения должны быть полностью бесплатными. Приложение должно быть полностью функциональным без покупок. Платными могут быть только дополнительные возможности (расширенная аналитика, интеграции, улучшенный AI), которые не влияют на базовую функциональность.
- **Принцип 7 — Memory как универсальная система знаний.** Memory — это не просто заметки, а единая система для любых источников информации (Obsidian, внутренние заметки, PDF, Telegram, и др.). Все источники индексируются в общий семантический поиск. Данные не дублируются, а подключаются через абстракцию источника.
- **Принцип 8 — Ролевая ответственность.** Каждая роль имеет строго определённые зоны ответственности. Архитектор анализирует и проектирует. Principal Architect проверяет и утверждает. Product Owner принимает финальное решение. Developer реализует по спецификации. Запрещено принимать решения "не своей ролью". Если Developer видит, что нужно изменить архитектуру — он останавливается и создаёт IMPLEMENTATION BLOCKER.
- **Принцип 9 — Пользовательские поля как метаданные.** Пользовательские поля не являются частью финансовой модели и не влияют на расчёт баланса, бюджета, долгов. Они используются только для дополнительной информации, фильтрации и отчётов.

## Правила работы с документацией

**Правило 1 — Готовь контекст.** Перед изменением открой нужные документы:

- База данных → Domain Model, Financial Rules, Database Spec, Architecture
- AI → AI System, Domain Model, Architecture
- Новая функция → Functional Requirements, Domain Model, Financial Rules, Architecture, Current State

**Правило 2 — Не придумывай новые разделы.** Если информации нет в текущей структуре → спросить: «В какой документ это положить?»

**Правило 3 — Приоритет при конфликтах:**

1. Domain Model
2. Financial Rules
3. Database Specification
4. Architecture
5. Functional Requirements
6. AI System
7. Current State
8. Development Log
При конфликте → сообщить мне, не править молча.

**Правило 4 — Версионирование.** Каждый документ: `Version: x.x` и `Last Updated: YYYY-MM-DD`. Изменения → в `09_Development_Log`.

**Правило 5 — Только Markdown.** Единый стиль, без лишнего форматирования, готовый к копированию.

**Правило 6 — Гибкость ссылок.** Для связывания документов и разделов можно использовать:

- Внутренние ссылки Obsidian в формате `[[Название документа]]` или `[[Название документа#Заголовок]]` для ссылки на конкретный раздел.
- Простые Markdown-ссылки вида `[текст](путь)` или прямое указание названия документа, если это удобно.
- Предпочтение отдаётся Obsidian-ссылкам для лучшей навигации внутри хранилища, но все перечисленные способы допустимы.

**Правило 7 — Открытые вопросы.** Если вопрос не решён, он остаётся в том документе, где возник, с пометкой `❓` и ссылкой на связанные разделы. Не создавать отдельного документа для нерешённых вопросов.

**Правило 8 — Планирование документации.** Перед началом разработки создаётся Documentation Plan. Документация изменяется только после завершения разработки и Code Review.
