## Общая модель системы

LifeOS построена вокруг операций. **Operation — источник истины.**

Поток данных:
Фото чека → AI → ParsedReceipt → Receipt → ReceiptResult (Receipt + Operation) → Operation → FinancialCalculator → FinancialState

## Сущности

### 1. Account

Источник денежных средств пользователя (карта, наличные, кредитка, накопительный счёт). Владелец операций.

**Поля:** id, name, type, initialBalance, isMain, icon, color (→ CardColorSettings).

**Связи:** Account → много Operation. Account → одна CardColorSettings.

Не хранит текущий баланс. Баланс = результат расчёта операций.

#### Полная настройка счетов

**Свободно изменяемые поля** (не влияют на операции):
- Название
- Иконка
- Цвет (через CardColorSettings)
- Описание
- Порядок (position)
- Основной счёт (isMain)

**Изменяемые с обработкой последствий** (требуют сценария миграции):
- Тип счёта — при смене типа система проверяет операции и предлагает миграцию с предупреждением
- Начальный баланс — через корректирующую операцию, а не прямое изменение

**Неизменяемые поля:**
- ID
- Валюта (изменение валюты = создание нового счёта)

### 2. CardColorSettings

Настройки цветового оформления карточки счёта для визуальной идентификации.

**Поля:** id, accountId, backgroundColor, textColor.

**Связи:** CardColorSettings ↑ Account (один к одному).

Бизнес-настройка пользователя, сохраняется через CardColorSettingsRepository.

### 3. ParsedReceipt

Промежуточная модель между AI-ответом и Receipt. Данные, извлечённые AI из чека.

**Поля:** merchant, date, totalAmount, items.

**Связи:** ParsedReceipt → ReceiptCreationService → Receipt.

DTO, не сохраняется в БД. Описан для полноты потока данных.

### 4. Receipt

Документ покупки из чека. Хранит факт покупки.

**Поля:** магазин, дата, сумма, фото, комментарий.

**Связи:** Receipt 1:N ReceiptItem. Receipt → ReceiptResult → Operation.

Не является финансовой операцией, сам не меняет баланс.
Изменение финансов: Receipt → ReceiptResult → Operation → Financial Rules.

### 5. ReceiptItem

Отдельная позиция внутри чека.

**Поля:** id, receiptId, name, category, quantity, price, totalPrice.

**Связи:** ReceiptItem ↑ Receipt. ReceiptItem ↓ Category.

Детализация покупки, не самостоятельная операция.

### 6. ReceiptResult

Транзакционная связка: результат обработки чека. Объединяет Receipt + Operation.

**Поля:** receipt, operation.

**Связи:** Receipt → ReceiptResult → Operation.

Обеспечивает атомарность: один чек → один ReceiptResult → один Receipt + одна Operation.
Не сохраняется как отдельная сущность, используется как возвращаемый тип сервиса.

### 7. Operation

**Основная финансовая сущность.** Движение денег. Все изменения системы — через операции.
Источник истины: Operation History.
Производные: баланс, финансовые состояния, бюджет, аналитика.

**Типы (OperationType):**
- expense — расход
- income — доход
- transfer — перевод между счетами
- repayment — погашение обязательства

**Поля:** id, type, amount, date, comment, shop, article, category, receiptId, accountId.

**Связи:**
- Receipt (через ReceiptResult): Receipt → ReceiptResult → Operation
- Account: Account → много Operation
- FinancialState: Operation → FinancialCalculator → FinancialState

**Источники создания:**
- Ручной ввод
- Receipt (фото → AI → ParsedReceipt → Receipt → ReceiptResult → Operation)
- Импорт (планируется)

### 8. Category

Классификация операций и позиций чеков. Группировка расходов, аналитика, бюджет, авто-правила.

**Текущее состояние:** модель Category, поле в Operation и ReceiptItem.

**Планируется:** полноценная сущность с пользовательскими категориями, авто-определением, связью с бюджетом.

### 9. FinancialState

Вычисленное финансовое состояние пользователя. Компоненты: баланс аккаунта, сумма доходов, сумма расходов.

Не источник истины. Источник: Operation.
Расчёт для каждого Account отдельно: Account → Operation → FinancialCalculator → FinancialState.

**Расположение:** lib/domain/entities/financial_state.dart (отдельно от сохраняемых моделей).
Вычисляется на лету, не сохраняется в БД.

### 10. Budget

📅 Планируется. Система планирования: план/факт, контроль лимитов.
Связи: Budget ↓ Category ↓ Operation.

### 11. Debt

📅 Планируется. Финансовая задолженность.

❓ Открытый вопрос: отдельная сущность или часть FinancialState.

### 12. Rule

📅 Планируется. Автоматическое правило обработки данных (ключевые слова, соответствия).
Из Legacy Google Sheets. Пример: "кредитка сбер" → Rule → Account: "Кредитка".

### 13. History

📅 Планируется. История изменений финансовой системы для аудита и восстановления.
Связь: Operation → History → FinancialState.

### 14. MemoryNote

⚠️ Будет изменено. Пользовательская заметка для семантического поиска. В текущей реализации содержит заголовок, текст, категорию, даты создания/обновления.

В будущем будет заменено универсальной системой знаний.

### 15. EmbeddingModel

Техническая модель, представляющая векторное представление фрагмента текста (чанка). Хранит:
- идентификатор источника (sourceType, sourceId)
- текст (content)
- вектор в виде BLOB
- модель и версию эмбеддинга
- временные метки
- метаданные (JSON)

Не является бизнес-сущностью. Используется только в системе знаний.

### 16. ObsidianNote

⚠️ Будет изменено. Модель заметки, импортированной из Obsidian Vault. Содержит id, path, title (очищенный от YAML-frontmatter), content, modifiedAt.

В будущем будет заменено универсальной системой знаний.

### 17. Product (Планируется)

Базовый продукт питания, который может быть добавлен вручную или импортирован из чека (ReceiptItem). Является источником истины для информации о продукте (название, категория, калорийность, БЖУ).

**Поля:** id, name, category, calories, proteins, fats, carbohydrates, unit (шт, г, мл, порция), createdAt, updatedAt.

**Связи:**
- Product 1:N FoodEntry (использование в приёмах пищи).
- Product 1:N InventoryItem (текущие остатки).

### 18. FoodEntry (Планируется)

Запись об использовании продукта в рамках конкретного приёма пищи (Meal) или самостоятельного события. Это **источник истины** для двух систем — журнала питания и инвентаря.

**Поля:** id, productId (FK → Product), mealId (FK → Meal, опционально), quantity, unit, timestamp.

**Ключевое поле:** consumptionState — "eaten" (съедено), "remaining" (осталось), "wasted" (выброшено).

**Связи:**
- FoodEntry ↑ Product.
- FoodEntry ↑ Meal (если в составе приёма).

### 19. InventoryItem (Планируется)

Представляет текущий остаток конкретного продукта, который хранится у пользователя дома. Это **кэш**, а не источник истины.

**Поля:** id, productId (FK → Product), quantity, unit, updatedAt (время последнего обновления остатка).

**Связи:**
- InventoryItem ↑ Product (One-to-One для продукта, у каждого продукта может быть только один текущий остаток).

**Примечание:** Количество в `InventoryItem` вычисляется и обновляется на основе событий потребления (`FoodEntry`), где `consumptionState = 'remaining'`. Это соответствует **Принципу 2 (Операции — источник истины)**.


### 20. Meal (Планируется)

Группа продуктов, потреблённых в один приём пищи (завтрак, обед, ужин, перекус). Позволяет управлять питанием как единым целым.

**Поля:** id, name (завтрак/обед), date, time, totalCalories (вычисляется), totalCost (вычисляется).

**Связи:**
- Meal 1:N FoodEntry.

## Концепция: Журнал питания и Инвентарь
Поток данных для инвентаризации:

Product (из чека/ручной ввод)  
↓  
FoodEntry (приём пищи или использование)  
├── consumptionState = 'eaten' → Журнал питания (Meal)  
├── consumptionState = 'remaining' → Инвентарь (InventoryItem)  
└── consumptionState = 'wasted' → Статистика потерь

text

**Важное архитектурное решение:** `FoodEntry` является единственным источником для *обоих* состояний: журнала питания и инвентаря. Это гарантирует согласованность и исключает дублирование информации (Принцип 4).

## Концепция: Knowledge Source

Система знаний строится вокруг абстракции источника. Это не финальная модель данных, а архитектурная концепция.

**Назначение:** Любой источник информации, который может быть проиндексирован и найден через семантический поиск.

**Примеры источников:**
- Obsidian Vault (md файлы) — реализовано
- Внутренние заметки приложения — реализовано (будет заменено)
- PDF-документы — планируется
- Telegram-сообщения — планируется
- Google Drive-файлы — планируется
- Email-письма — планируется
- Голосовые заметки (транскрипция) — планируется
- Изображения (OCR + описание) — планируется

**Принципы:**
- Единый интерфейс для всех источников
- Каждый источник предоставляет: текст, метаданные, уникальный идентификатор
- Индексация и поиск — общие для всех источников
- Конфиденциальность: источники с чувствительными данными помечаются соответствующим образом

## Концепция: Receipt Draft

Новая сущность для объединения нескольких фото в один чек.

**Назначение:** Черновик чека, позволяющий добавлять несколько фотографий перед распознаванием.

**Жизненный цикл:**
Receipt Draft (создание)
↓
Добавление фотографий (одна или несколько)
↓
Редактирование фотографий (удаление, изменение порядка, замена)
↓
Распознавание (AI)
↓
Receipt (финальный)
↓
Operation

**Поля (предварительно):**
- id — UUID
- createdAt — дата создания
- updatedAt — дата последнего изменения
- status — draft, processing, completed, failed
- photoPaths — список путей к фотографиям (порядок важен)
- parsedData — результат AI (если уже распознавался)
- receiptId — ссылка на финальный Receipt (после завершения)
- error — сообщение об ошибке (если failed)

Не является финансовой операцией. Только черновик.

## Конфиденциальность и чувствительные данные

Следующие данные считаются чувствительными и не должны передаваться вовне без явного согласия пользователя:

- Финансовые данные: суммы, счета, операции, категории
- Персональные данные: имена, адреса, контакты
- Фотографии чеков: могут содержать личную информацию
- Заметки: могут содержать личные мысли, планы, идеи
- История операций: полная финансовая история пользователя

**Принцип обработки:**
- Все данные хранятся локально (SQLite, файловая система)
- Внешние AI-вызовы (OpenRouter) отправляют только:
  - Для распознавания чеков: фотографию (временная отправка, не сохраняется)
  - Для эмбеддингов: текст (временная отправка, не сохраняется)
- Никакие данные не передаются третьим лицам
- API-ключи используются только для авторизации запросов

## Что НЕ является бизнес-сущностью

- Фото чека — источник создания Receipt (UI/ввод данных)
- AI JSON — промежуточный формат
- ParsedReceipt — DTO на границе AI и доменной модели
- ReceiptResult — транзакционная обёртка (не сохраняется)
- Баланс — результат вычисления, не объект хранения
- Технические модели системы знаний (MemoryChunk, MemorySource, MemorySearchResult) — относятся к [[06_AI_System]]

---

## Основные принципы модели

1. Operation — источник истины
2. Движение денег — все изменения через Operation
3. Владение — Account владеет операциями
4. Расчётность — FinancialState вычисляется, не хранится
5. Документирование — Receipt описывает покупку, не меняет финансы
6. Детализация — ReceiptItem детализирует покупку, не операция
7. Транзакционность — ReceiptResult = атомарная связка Receipt + Operation
8. AI — инструмент ввода — создаёт данные, не определяет логику
9. Независимость модели — бизнес-модель не зависит от технической реализации
10. Приватность по умолчанию — все данные локальные, внешние вызовы только с согласия пользователя

## Открытые вопросы

❓ Связь Receipt и Operation — может ли один чек создавать несколько операций?
❓ Связь ReceiptItem и Operation — только детализация или отдельная операция?
❓ Финальная модель категорий — отдельная таблица, пользовательские категории, связь с Budget и Rule?
❓ Финальная модель долгов — отдельная сущность Debt или часть FinancialState?
❓ Перенос FinancialState — из lib/domain/entities/ в lib/models/ при кэшировании?
❓ Модель данных для Knowledge Source — финальное название и структура (KnowledgeItem, Note, Document, SourceEntry)
❓ Механизм изменения начального баланса — через корректирующую операцию или отдельный метод?
❓ Какие функции будут платными? — требуется чёткое разделение между бесплатной и платной версией
❓ Нужно ли шифровать локальную БД? (SQLCipher или другая технология)

## Итоговая модель

Факты (фото чеков) → AI (ParsedReceipt) → Бизнес-сущности (Receipt → ReceiptResult → Operation) → Расчёты (FinancialCalculator) → Финансовое состояние (FinancialState)

AI ускоряет ввод. Бизнес-логика — внутри приложения. Operation — единственный источник истины.

Система знаний (Memory) — универсальный слой поверх всех источников информации, обеспечивающий семантический поиск без привязки к конкретному типу источника.
