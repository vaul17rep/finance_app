## Основные финансовые принципы

### 1. Операции — источник истины

❌ `Карта Сбер = 15000` и менять число
✅ `Доход +50000 → Расход -5000 → Перевод -3000 → Расчёт состояния`

Баланс — результат обработки операций.

### 2. Финансовая логика отделена от хранения

База хранит факты. Financial Rules определяют, как факты влияют на состояние.

### 3. Financial State — результат расчёта

Не самостоятельный источник. `Operation → Financial Rules → Financial State`.
❌ Нельзя изменять Financial State напрямую.

### 4. Каждая операция имеет финансовое влияние

Определяет: источник денег, направление движения, изменение состояния.

### 5. Приватность финансовых данных

Финансовые данные являются чувствительными и требуют особой защиты:

- Все операции, счета, чеки хранятся только локально
- Нет облачной синхронизации по умолчанию
- AI-обработка (распознавание чеков) отправляет только фото, данные не сохраняются
- Все внешние вызовы логируются

## Типы операций (принятые)

| Тип | Влияние | Пример |
| ----- | --------- | -------- |
| `income` | Баланс + | Зарплата, поступления |
| `expense` | Баланс − | Покупка, оплата услуги |
| `transfer` | Счёт А −, Счёт Б + | Перевод между картами |
| `debt_repayment` | Баланс −, Долг − | Погашение кредита |

**Решение:** Добавлены типы `transfer` и `debt_repayment`. (Ранее было "не решено")

## Категории (принятое решение)

### Назначение

Классификация операций и товаров для аналитики, бюджета, отчётов.

### Правила

- **Категория — только у ReceiptItem.** У чека категории нет.
- Отдельная таблица `categories` с пользовательскими категориями.
- Иерархия категорий (родитель-потомок).
- Авто-определение категории при распознавании чека (AI + правила пользователя).
- У Operation категория — опционально (кэш для быстрого доступа).

**Решение:** Категория только у ReceiptItem. (Ранее было "не решено")

## Долги (принятое решение)

### Модель

- **Отдельная сущность `Debt`**, не часть Financial State.
- Таблица `debts` + `debt_payments` (история погашений).

### Правила

- Создание долга: ручное (личные долги).
- Погашение долга: создаётся **Operation типа `debt_repayment`**, связанная с `debtId`.
- Долг **не влияет** на бюджет напрямую. Влияет только операция погашения.
- Просроченные долги остаются видимыми до ручного закрытия.
- Статусы долга: `active` / `partial` / `closed` / `overdue`.

### Отображение

- Отдельный экран со списком долгов.
- На Home Screen — блок «Просроченные долги» (всегда виден).
- Напоминания за 3 дня до срока.

**Решение:** Долг — отдельная сущность. Погашение через Operation. (Ранее было "не решено")

## Бюджет (принятое решение)

### Модель

- `budget_periods`: id, name, startDate, endDate, status (active/archived)
- `budget_items`: id, periodId, categoryId, plannedAmount

### Период

- **Пользовательский.** По умолчанию: от зарплаты до зарплаты (дата следующего дохода).
- Ручная настройка: выбор даты начала/конца.

**Решение:** Пользовательский период (от зарплаты до зарплаты по умолчанию). (Ранее было "не решено")

### Расчёт

- **Доходная часть:** сумма операций `income` за период.
- **Расходная часть:** сумма операций `expense` по категориям (из ReceiptItem).
- **Остаток:** доходы − расходы − плановые накопления.
- **Прогресс по категории:** spent / planned × 100%.

**Решение:** Формула остатка = доходы − расходы − накопления. (Ранее было "не решено")

### Правила

- Бюджет — **план**, а не учёт. Сравнивается с фактом из операций.
- Платежи по долгам — отдельная категория в бюджете.
- Предупреждения при превышении 80% и 100% лимита.
- История периодов с возможностью сравнения.

## Возвраты (принятое решение)

### Правило

Возврат — **отдельное финансовое событие.**

- Создаётся новая операция типа `expense` с отрицательной суммой (или `refund`).
- Связь с исходной операцией через поле `originalOperationId`.
- Возврат не изменяет исходную операцию (сохраняется история).

**Решение:** Новая операция со ссылкой на исходную. (Ранее было "не решено")

## Пользовательские поля (Custom Fields)

### Назначение

Дать пользователю возможность добавлять произвольные метаданные к операциям, чекам, товарам и заметкам без изменения финансовой логики.

### Правила

- Пользовательские поля **не влияют** на расчёт баланса, бюджета, долгов.
- Они используются только для:
  - Дополнительной информации (проект, клиент, место)
  - Фильтрации и сортировки в списках
  - Группировки в отчётах
- Поля могут быть обязательными или опциональными.
- Типы полей: текст, число, дата, булево, выбор из списка, мультивыбор.

### Хранение

- Определения полей — в `custom_field_definitions`.
- Значения — в `custom_field_values` (JSON).
- Связь с сущностями через `entityId` + `entityType`.

### UI

- Пользователь управляет определениями через экран настроек.
- Поля отображаются в карточках сущностей и формах создания/редактирования.
- Фильтры по пользовательским полям доступны в списках.

## Миграция данных при изменении счёта

### Свободно изменяемые поля (не влияют на операции)

- Название
- Иконка
- Цвет
- Описание
- Порядок
- Основной счёт

### Изменяемые с обработкой последствий (требуют сценарий миграции)

**Тип счёта (например, credit → debit):**

- При смене типа необходимо проверить все операции, связанные со счётом
- Если операции есть — показать предупреждение: "Изменение типа счёта повлияет на историю операций. Продолжить?"
- После подтверждения — выполнить миграцию данных (пересчёт категорий, переклассификация операций)
- Если миграция невозможна — заблокировать изменение с объяснением причины

**Начальный баланс:**

- Нельзя просто изменить значение
- Нужен отдельный механизм: создание корректирующей операции (например, "Корректировка начального баланса")
- Или: создание новой операции типа `adjustment` с комментарием

**Решение:** Корректирующая операция. (Ранее было "не решено")

### Неизменяемые поля

- ID (идентификатор)
- Валюта (изменение валюты = миграция всей финансовой истории, что практически равно созданию нового счёта)

## Финансовые состояния (Account Types)

### Общий принцип

Место хранения/учёта денег. Каждое состояние имеет свои правила изменения.

### Дебетовая карта (debit)

Доход → баланс+. Расход → баланс-.

### Наличные (cash)

Доход → наличные+. Расход → наличные-.

### Кредитная карта (credit)

Обязательство перед банком. Покупка → долг+. Погашение → долг-.

### Бонусный счёт / Рабочий лимит (work_benefit)

- Отдельная сущность (не Account), остаток вычисляется из истории операций.
- Используется для кешбэка, бонусов, подарочных карт.
- Отображение в виджете выбора.

## Финансовые ограничения

1. ❌ Баланс нельзя менять вручную
2. ❌ Финансовая логика не зависит от UI
3. ❌ Финансовая логика не зависит от базы данных
4. ❌ AI не принимает финансовые решения
5. Финансовые состояния = результат обработки операций
6. Financial State не изменяется напрямую: `Operation → Financial Rules → Financial State`

## Модель распространения (финансовый аспект)

### Бесплатная версия (полностью функциональна)

- Неограниченное количество операций, счетов, чеков (локально)
- Базовое AI-распознавание чеков (ограниченное количество)
- Базовый семантический поиск (локальные эмбеддинги)
- Бюджетные периоды (план/факт)
- Долги и планы покупок
- **Пользовательские поля (до 5 полей на сущность)**
- Все основные настройки
- Локальное хранение всех данных

### Платная версия (расширенные возможности)

- Безлимитное AI-распознавание чеков
- Расширенный семантический поиск (улучшенное качество, больше источников)
- Расширенная аналитика и отчёты
- Синхронизация между устройствами
- Интеграции (Google Drive, Telegram, Email, PDF, голосовые заметки)
- Data Quality Score и рекомендации
- **Безлимитные пользовательские поля**

**Принцип:** Платная версия добавляет удобство, но не является необходимой для базового использования. Бесплатная версия — полноценный продукт.
