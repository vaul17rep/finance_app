## Назначение

AI-подсистема LifeOS. Как AI участвует в работе приложения.

---

## Главная идея

AI — инструмент автоматического распознавания данных и структурирования информации.

- AI: "Что находится на чеке?"
- Финансовая система: "Что это означает для финансов?"

AI **отвечает за:** анализ изображения, распознавание текста, извлечение информации, структурирование данных, создание эмбеддингов.
AI **НЕ отвечает за:** изменение баланса, расчёт состояний, бюджет, финансовые правила, прямой доступ к БД.

---

## Общий поток данных

Фото → Compression → Base64 → OpenRouter API → JSON → ParsedReceipt → Receipt → ReceiptItem → Operation → Repository → SQLite → Financial System

---

## Архитектурный принцип

Нельзя: Фото → AI → SQLite (AI не владеет данными)
Правильно: Фото → Compression → Base64 → AI API → JSON → ParsedReceipt → Domain Models → Repository → SQLite → Financial Logic

---

## AI Provider

- Провайдер: OpenRouter API
- Endpoint: https://openrouter.ai/api/v1/chat/completions
- Метод: POST

## AI Model

- Текущая: openai/gpt-4o-mini
- Причины: поддержка изображений, качество, низкая стоимость, скорость. Модель может меняться без изменения архитектуры.

## AI Flow

### Input
- Источник: камера или галерея (image_picker)

### Processing
Пользователь → ImagePicker → File → Compression → Base64 → OpenRouter API → JSON → ParsedReceipt → Receipt → ReceiptItem → Operation → SQLite

### Output
AI JSON → ParsedReceipt → Application Models → Database

## Image Processing

- Получение: image_picker (Camera / Gallery)
- Compression: сжатие перед отправкой (уменьшение размера, ускорение, снижение стоимости)
- Кодирование: File.readAsBytes() → Base64 → data:image/jpeg;base64,...

## Prompt System

Промпт отвечает за: распознавание чека, магазин, дату/время, товары, категории. Только JSON.

**Игнорировать:** рекламу, юридическую информацию, даты регистрации, служебные данные.  
Полный промпт в коде OpenRouterService.

**Последние изменения:**

- +address, +comment (чек)
    
- +price_before_discount, +comment (товар)
    
- Уточнены правила количества, единиц, способа оплаты
    
- Запрет придумывать данные

## User Note Processing

Пользователь может добавить контекст (например, "Оплата с карты Сбер").

Поток: Image + User Note → AI Model → Structured JSON

**Правило:** если указан источник оплаты — использовать, иначе — только из чека.  
AI нельзя придумывать источник, создавать несуществующие данные.

suggested_account — планируется, но не в текущей схеме. AI не создаёт/не меняет Account.

## JSON Schema

json

```
{
  "date": "ДД.ММ.ГГГГ",
  "time": "ЧЧ:ММ",
  "store": "",
  "address": "",
  "payment_type": "",
  "comment": "",
  "total_amount": 0,
  "items": [
    {
      "product": "",
      "category": "",
      "quantity": 0,
      "unit": "",
      "price_per_unit": 0,
      "total_price": 0,
      "price_before_discount": 0,
      "comment": ""
    }
  ]
}
```

**Назначение полей:**

- date, time — дата и время покупки
    
- store — магазин
    
- address — адрес (если указан)
    
- payment_type — карта, наличные, кредит
    
- comment (чек) — при сомнениях в читаемости
    
- total_amount — общая сумма
    
- items: product, category, quantity, unit, price_per_unit, total_price, price_before_discount, comment

## ParsedReceipt

Промежуточный объект между AI и приложением. Разделяет AI-слой и финансовую систему.  
AI JSON → ParsedReceipt → Receipt → ReceiptItem → Operation  
Не финансовая сущность, не меняет баланс, не сохраняется в БД.

---

## Правила категорий

Основные: мясо, рыба, молочка, овощи, фрукты, бакалея, напитки, сладкое, бытовое, другое.  
Специальные: молочные продукты → молочка, вода/соки/газировка → напитки, мороженое → сладкое.

---

## Создание финансовых операций

После сохранения чека → Operation. Текущая логика: один чек = одна операция расхода.  
Будущее: Receipt → Financial Rules → Multiple Operations.

## Ошибки OpenRouter

- 401: неверный ключ
    
- 402: нет средств → AiLimitException с балансом
    
- 403: ограничения доступа
    
- 404: недоступная модель/endpoint → проверить AiProfile
    
- 429: превышение лимита → пометить ключ, использовать другой

### Логирование ошибок OpenRouter

При ошибках 400 и 403 в лог записывается полный ответ API (включая тело). Это позволяет диагностировать:

- Неверный формат запроса
- Проблемы с аутентификацией
- Недостаток средств на аккаунте (`insufficient_balance`)
- Ограничения доступа к модели

Логирование выполняется через `DebugLogger` с тегом `AI`.

## Валидация текста для эмбеддингов

Перед отправкой запроса к OpenRouter текст валидируется:

- Пустые тексты (`text.trim().isEmpty`) → выбрасывается исключение
- Тексты короче 3 символов → выбрасывается исключение

Это предотвращает бесполезные API-запросы и экономит ресурсы.

## Взаимодействие с Background Manager

Фоновые задачи могут запускать AI-процессы (распознавание, переиндексация системы знаний).  
Механизм: BackgroundTaskManager → BackgroundTask (тип ai_recognize) → OpenRouterService.analyzeReceipt() → результат/ошибка → БД через репозитории.

Все AI-запросы из фона используют те же ключи/профили. Рекомендуется ограничивать число одновременных запросов.

## Конфиденциальность и AI

### Принципы

1. Минимальные данные: внешние AI-сервисы получают только те данные, которые необходимы для выполнения конкретной задачи
    
2. Временная обработка: данные не сохраняются на стороне провайдера дольше, чем необходимо для обработки запроса
    
3. Согласие пользователя: пользователь явно соглашается на отправку данных в AI (при первом использовании функции)
    
4. Прозрачность: пользователь видит, какие данные отправляются и куда (через логи)
    

### Что отправляется в OpenRouter

|Функция|Отправляемые данные|Сохраняется ли|
|---|---|---|
|Распознавание чека|Фото (Base64), промпт|Не сохраняется (временная обработка)|
|Создание эмбеддинга|Текст (часть заметки или чека)|Не сохраняется (возвращается вектор)|
|(Будущее) Анализ данных|Анонимизированные данные|Не сохраняется|

### Что НЕ отправляется

- Полная финансовая история
    
- Личные данные (имена, адреса, контакты)
    
- Номера счетов, карт
    
- Пароли и ключи
    

### Контроль

- Все AI-запросы логируются в локальный logs.txt
    
- Пользователь может отключить AI-функции в настройках
    
- Пользователь может удалить все отправленные данные (очистка кэша)

## Система знаний (семантический поиск)

### Назначение

Обеспечивает семантический поиск по всем источникам информации на основе векторных представлений (эмбеддингов).

### Архитектура

- Абстракция: VectorSearchService – позволяет сменить движок поиска
    
- Реализация: SqliteVectorSearchService – хранение векторов в BLOB, косинусное сходство в памяти
    
- Управление индексацией: IndexingService – индексация источников, поддержка частичной и полной переиндексации
    
- Получение эмбеддингов: EmbeddingService – использует OpenRouter API (настраивается)
    

### Модель эмбеддингов

- По умолчанию: openai/text-embedding-3-small
    
- Возможность смены модели через настройки
    
- При смене модели требуется ручная переиндексация всех данных
    

### Автоматическая индексация

- Включена по умолчанию (настраивается в Settings → AI / Поиск)
    
- При создании чека запускается фоновый процесс индексации
    
- При редактировании чека запускается переиндексация только этого чека
    
- Индексация асинхронна и не блокирует UI
    

### Ручная индексация

- Доступна в настройках: "Переиндексировать все данные" с выбором источников
    
- Используется при смене модели, восстановлении данных или отключении автоиндексации


    

### UI поиска

- Экран Memory содержит поле ввода, кнопку поиска и список результатов
    
- Результаты отображаются с типом источника, заголовком, датой и фрагментом текста
    
- По нажатию на результат выполняется переход к соответствующему объекту
    

### Ограничение результатов

- По умолчанию 10 результатов, можно расширить до 20
    

### Контроль актуальности

- Поля sourceUpdatedAt и embeddingUpdatedAt позволяют определять устаревшие эмбеддинги
    
- При изменении источника удаляется старый эмбеддинг и создаётся новый
    

### Индексация Obsidian Vault

Пользователь выбирает папку Vault в Настройках (AI / Memory → Obsidian Vault).  
На экране Memory появляется кнопка "Индексировать Obsidian", запускающая процесс.  
IndexingService.indexObsidian() считывает все .md файлы, очищает YAML-фронтматтер, генерирует эмбеддинги и сохраняет в таблицу embeddings с sourceType = 'obsidian_note'.  
Результаты поиска отображаются с пометкой "Obsidian".

### Индексация Obsidian — улучшения

**Идентификация документов:**
- `sourceId` теперь является стабильным идентификатором документа (хеш пути), а не путём
- Физический путь сохраняется в `metadata.path` для обратной совместимости и отладки
- Это позволяет корректно обрабатывать перемещение и переименование файлов

**Инкрементальная индексация:**
- Перед индексацией файла проверяется наличие любых эмбеддингов с `sourceId` документа
- Сравнивается `sourceUpdatedAt` с `modifiedAt` файла
- Если файл не изменился — пропускается
- Для больших файлов проверка выполняется корректно (по всем чанкам)

**Чанкинг (разбивка на части):**
- Файлы размером > 5000 символов автоматически разбиваются на чанки через `ChunkingService`
- Каждый чанк получает метаданные: `chunkIndex`, `totalChunks`, `parentTitle`
- Все чанки одного документа имеют одинаковый `sourceId`
- Результаты поиска группируются по `sourceId` (один документ → один результат)

**Пакетная обработка:**
- Размер пачки: 30 файлов
- Пауза между пачками: 100 мс
- Параллельность внутри пачки: 5 одновременных запросов

**Прогресс в UI:**
- Колбэк `onProgress(int processed, int total)` в `indexObsidian()`
- Отображение в AppBar: `обработано N из M`

**Отчёт по окончании:**
- Всего файлов, успешно, пропущено (без изменений), ошибок
- Список ошибок с именами файлов
- Количество созданных чанков

**Фильтрация служебных папок:**
- `.trash/`, `.obsidian/`, `.git/`, `.stversions/`
- Конфликтные файлы `.sync-conflict-*`

**Очистка битых эмбеддингов:**
- Автоматическая очистка при инициализации `SqliteVectorSearchService`
- Асинхронное удаление битых векторов при обнаружении во время поиска
- Кнопка в MemoryScreen с диалогом подтверждения
- Проверка существования таблицы перед операцией
- Удаление записей с `LENGTH(vector) % 4 != 0`
- Предложение переиндексации после очистки

### Миграция sourceId

При обновлении системы выполняется безопасная миграция индекса Obsidian:

1. **Backup:** создаётся резервная копия БД
2. **Создание нового индекса:** все Obsidian-записи переиндексируются с новым `sourceId` (хеш пути) и `migrationId` в метаданных
3. **Валидация:** проверяется, что создано не менее 90% от исходного количества записей
4. **Удаление старого индекса:** при успешной валидации удаляются старые записи
5. **Очистка:** из метаданных удаляется временное поле `migrationId`

При неудаче миграции (менее 90% записей) новый индекс удаляется, старый сохраняется.

**Атомарность операции:**
- Сначала создаются все новые чанки
- Только после успешного сохранения удаляется старый эмбеддинг
- Если ни один чанк не сохранён, метод выбрасывает исключение, и старые данные остаются нетронутыми
- Это гарантирует отсутствие потери данных при частичных ошибках

**Валидация текста:**
- Пустые тексты и тексты короче 3 символов пропускаются без создания API-запроса
- Это предотвращает бесполезные запросы к OpenRouter

## Текущие проблемы AI

- Дата: иногда выбирается дата печати вместо покупки → усиливаем промпт
- Время: может отсутствовать → доп. инструкции
- Категории: только текст, нет системы → создание Category System
- Скорость: зависит от размера изображения, Compression, API, модели → улучшать сжатие, оптимизировать промпт
- ⚠️ **Качество семантического поиска** — частично улучшено (внедрён чанкинг для длинных текстов, группировка результатов), но полное решение требует перехода к универсальной системе знаний (KnowledgeSource)

## Главный принцип AI-модуля

AI — инструмент ввода данных и структурирования информации.  
**AI:** "Что находится в данных?"  
**Приложение:** "Как это влияет на систему?"

AI может: распознавать, структурировать, предлагать.  
Не может: управлять финансами, менять состояние, создавать сущности, иметь прямой доступ к БД, принимать решения.
