## Главный принцип процесса

### Принцип 1 — Никаких догадок

System Architect, Principal Architect и Developer не имеют права предполагать существование кода.

**Запрещено утверждать:**
- существование методов
- существование классов
- структуру проекта
- поток выполнения

**Правильно:** запросить нужный файл или уточнить контекст.

### Принцип 2 — Одно изменение — один этап

Архитектор проектирует. Developer реализует. Knowledge Manager документирует.

Нельзя совмещать роли в одном действии. Нельзя перепрыгивать через этапы.

### Принцип 3 — Архитектура утверждается до разработки

Implementation Specification создаётся только после утверждения:
- System Architect → Principal Architect → Product Owner

Без утверждения — разработка не начинается.

### Принцип 4 — Разработчик не принимает архитектурных решений

Если в процессе реализации выясняется, что требуется изменить архитектуру, модель данных или API — Developer обязан остановиться и создать IMPLEMENTATION BLOCKER.

## Роли и ответственность

### System Architect

**Phase 1 — Architecture Analysis**

Задача:
- анализ проблемы
- диагностика (если требуется)
- Impact Analysis (оценка влияния изменений)
- варианты решения
- Red Flags (риски и предупреждения)
- Rollback Thinking (возможность отката)
- подготовка **Architect Brief**

После этого работа архитектора останавливается.

Implementation Specification на этом этапе не создаётся.

**Phase 2 — Implementation Specification**

Запускается только после:
- Approved от Principal Architect
- утверждения Product Owner

На этом этапе архитектор:
- не пересматривает архитектуру
- не ищет новые варианты
- не принимает новые решения

Архитектор **преобразует утверждённую архитектуру** в техническую спецификацию реализации.

**Что запрещено архитектору:**
- изменять код
- принимать финальные решения без утверждения
- переходить к Phase 2 до утверждения Phase 1

---

### Principal Architect

Задача:
- проверка Architect Brief
- проверка Implementation Specification
- утверждение архитектуры
- выявление Red Flags
- оценка возможности отката

**Правила:**
- Без утверждения Principal Architect — дальше нельзя
- Principal Architect не пишет код
- Principal Architect не принимает бизнес-решений

---

### Product Owner

Задача:
- утверждение или отклонение спецификации
- принятие финального решения о реализации

**Правила:**
- Без утверждения Product Owner — разработка не начинается
- Product Owner не анализирует архитектуру
- Product Owner не проверяет код

---

### Developer

Задача:
- реализация кода строго по Implementation Specification
- указание точного места изменения
- создание IMPLEMENTATION BLOCKER при необходимости

**Требования к указанию места изменения:**

Запрещены формулировки:
- "найдите место"
- "где-нибудь"
- "после нужного метода"
- "создайте похожий"

Каждое изменение должно содержать:
- полный путь файла
- класс
- метод
- точную точку вставки (ориентир между какими элементами производится изменение)

**Когда Developer обязан остановиться:**

Если требуется:
- изменить архитектуру
- изменить модель данных
- изменить API
- изменить поток
- изменить принятые решения

Developer создаёт **IMPLEMENTATION BLOCKER** и возвращает задачу архитектору.

**Что запрещено разработчику:**
- принимать архитектурные решения
- изменять модель данных без согласования
- обходить спецификацию

---

### Knowledge Manager

**Phase 1 — Documentation Planning**

Выполняется до начала реализации.

Задача:
- определить какие документы и разделы будут затронуты
- подготовить план изменений документации

Документация на этом этапе **не изменяется**.

**Phase 2 — Documentation Update**

Выполняется после:
- реализации
- Code Review

Задача:
- обновить документы
- обновить Development Log
- сформировать итоговый Documentation Update Report

**Что запрещено Knowledge Manager:**
- изменять документацию без плана
- изменять документацию до завершения разработки

└── Если утверждено → Передаётся System Architect

└── System Architect

└── Knowledge Manager

└── Передаётся Developer

Development
└── Developer
└── Реализует код строго по спецификации
└── Если нужно изменить архитектуру → IMPLEMENTATION BLOCKER → возврат к шагу 1
└── Передаётся на Code Review

Code Review
└── Проверка кода
└── Если есть замечания → возврат к шагу 6
└── Если OK → Передаётся Knowledge Manager

Documentation Update
└── Knowledge Manager
└── Обновляет документы
└── Обновляет Development Log
└── Создаёт Documentation Update Report

## IMPLEMENTATION BLOCKER

### Когда создаётся

Если в процессе разработки Developer обнаруживает, что нужно:

- изменить архитектуру
- изменить модель данных
- изменить API
- изменить поток
- изменить принятые решения

### Структура BLOCKER
IMPLEMENTATION BLOCKER

Задача: [ссылка на задачу или номер задачи]
Спецификация: [что утверждено в Implementation Specification]
Проблема: [что не получается реализовать]
Причина: [почему спецификация не работает]
Предложение: [что нужно изменить]

text

### Действия после BLOCKER

1. Developer останавливает работу над задачей
2. Задача возвращается архитектору
3. Архитектор анализирует проблему
4. Процесс начинается с шага 1 (Architecture Analysis)

## Финальный критерий хорошего решения

Решение считается правильным, если:

1. сохранён смысл бизнес-модели
2. соответствует Financial Rules
3. находится в правильном архитектурном слое
4. не нарушает Operation Source of Truth
5. не создаёт лишних зависимостей
6. сохраняет конфиденциальность данных
7. не нарушает принцип бесплатной работающей версии
8. не требует изменения кода для пользовательских сценариев
9. учитывает миграцию данных при изменении сущностей
10. понятно будущему разработчику
11. уменьшает технический долг
12. **решения были проверены и утверждены на всех этапах процесса**
