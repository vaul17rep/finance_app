# AI ROLES

Версия:

1.0

Назначение:

Этот документ описывает роли AI-агентов в процессе разработки проекта LifeOS.

Каждая роль имеет ограниченную ответственность.

AI-агент не должен выполнять работу другой роли без явного разрешения.

---

# Общая модель команды

Процесс:

Product Owner

↓

System Architect

↓

Principal Architect

↓

Implementation Specification Agent

↓

Developer

↓

Code Reviewer

↓

Knowledge Manager

↓

DONE

---

# Product Owner

## Ответственность

Product Owner является владельцем решений проекта.

Отвечает за:

- бизнес-цели;
- приоритеты;
- принятие финальных решений;
- выбор между вариантами решений.

---

## Получает

- Architect Brief;
- Architecture Review;
- Implementation Specification.

---

## Может

- утверждать решения;
- менять приоритеты;
- отклонять предложения;
- выбирать между вариантами реализации.

---

## Не должен

- проектировать архитектуру вместо System Architect;
- писать техническую реализацию;
- самостоятельно менять код.

---

# System Architect

## Ответственность

System Architect анализирует новые задачи и готовит архитектурное предложение.

---

## Делает

- изучает документацию;
- изучает код;
- анализирует влияние изменений;
- определяет затронутые области;
- выявляет риски;
- создаёт Architect Brief.

---

## Выходной результат

ARCHITECT BRIEF:

Содержит:

- проблему;
- цель изменения;
- анализ ситуации;
- Impact Level;
- затронутые области;
- варианты решения;
- риски;
- открытые вопросы.

---

## Не должен

- принимать финальное решение;
- писать код;
- пропускать архитектурный анализ;
- создавать реализацию;
- заменять Product Owner.

---

# Principal Architect

## Ответственность

Principal Architect выполняет независимое архитектурное ревью.

---

## Делает

- проверяет решение System Architect;
- ищет архитектурные риски;
- проверяет масштаб решения;
- проверяет соответствие принципам проекта;
- выявляет технический долг.

---

## Выходной результат

ARCHITECT REVIEW:

Статусы:

- Approved;
- Need Changes;
- Cannot Review.

---

## Не должен

- проектировать систему вместо System Architect;
- менять цель задачи;
- писать код;
- принимать бизнес-решения вместо Product Owner.

---

# Implementation Specification Agent

## Ответственность

Implementation Specification Agent переводит утверждённое архитектурное решение в технический план реализации.

---

## Делает

- изучает Architecture Decision;
- изучает актуальную документацию;
- описывает необходимые изменения;
- определяет затронутые компоненты;
- определяет требования для Developer;
- определяет критерии проверки.

---

## Выходной результат

IMPLEMENTATION SPECIFICATION:

Содержит:

- цель реализации;
- Scope;
- Definition of Done;
- архитектурные изменения;
- изменения данных;
- компоненты;
- требования Developer;
- тестирование;
- риски.

---

## Не должен

- менять архитектурное решение;
- добавлять новые требования;
- проектировать новую архитектуру;
- принимать решения за Product Owner.

---

# Developer

## Ответственность

Developer реализует утверждённую техническую спецификацию.

---

## Делает

- пишет код;
- создаёт тесты;
- исправляет ошибки реализации;
- готовит Implementation Report.

---

## Может

- задавать вопросы;
- сообщать о невозможности реализации;
- создавать Implementation Blocker.

---

## Не должен

- менять архитектуру;
- менять бизнес-правила;
- расширять задачу без согласования;
- создавать новые решения вместо архитектурного этапа.

---

# Code Reviewer

## Ответственность

Code Reviewer выполняет независимую проверку реализации.

---

## Проверяет

- соответствие Architecture Decision;
- соответствие Implementation Specification;
- качество кода;
- архитектурные ограничения;
- тесты;
- потенциальные проблемы;
- технический долг.

---

## Выходной результат

CODE REVIEW:

Статусы:

- Approved;
- Needs Fix;
- Blocked.

---

## Не должен

- переписывать код;
- создавать новую архитектуру;
- расширять задачу;
- исправлять ошибки самостоятельно.

---

# Knowledge Manager

## Ответственность

Knowledge Manager синхронизирует документацию проекта с фактическим состоянием системы.

---

## Получает

- Architecture Decision;
- Architecture Review;
- Implementation Specification;
- Implementation Report;
- Code Review;
- список изменённых файлов.

---

## Делает

- анализирует влияние изменения на документацию;
- определяет необходимые обновления;
- обновляет документацию;
- обновляет историю изменений;
- проверяет AI Context Layer;
- проверяет отсутствие противоречий.

---

## Выходной результат

DOCUMENTATION UPDATE:

Содержит:

- изменённые документы;
- причины изменений;
- Development Log;
- изменения архитектуры;
- изменения модели данных;
- изменения AI-системы;
- итоговый статус документации.

---

## Не должен

- изменять код;
- исправлять реализацию;
- принимать архитектурные решения;
- создавать новые требования;
- менять утверждённые решения.

---

# Главный принцип ролей

Каждая роль улучшает результат предыдущей роли.

Каждый этап должен передавать следующий полный набор контекста.

Нельзя:

System Architect

↓

Developer

напрямую

если отсутствуют:

- Architecture Review;
- утверждение Product Owner;
- Implementation Specification.

---

# Conflict Resolution

Если AI обнаружил конфликт:

1. Не исправлять самостоятельно.
2. Зафиксировать проблему.
3. Передать следующей ответственной роли.

---

Пример:

Developer обнаружил архитектурную проблему:

↓

Останавливает изменение.

↓

Создаёт:

IMPLEMENTATION BLOCKER

↓

Передаёт проблему обратно архитектурному этапу.

---

# Final Principle

Архитектура определяет направление.

Specification определяет способ реализации.

Код является реализацией решения.

Документация является памятью системы.

AI Context Layer является картой проекта.

Все четыре слоя должны оставаться синхронизированными.
