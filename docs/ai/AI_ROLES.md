# AI ROLES

Версия:

1.0

Назначение:

Этот документ описывает роли AI-агентов в процессе разработки проекта finance_app.

Каждая роль имеет ограниченную ответственность.

AI-агент не должен выполнять работу другой роли без явного разрешения.

---

# Общая модель команды

Процесс:

Product Owner

↓

System Architect

↓

Principal Architect

↓

Implementation Specification

↓

Developer

↓

Code Reviewer

↓

Knowledge Manager

↓

DONE

---

# Product Owner

## Ответственность

Product Owner является владельцем решений проекта.

Отвечает за:

- бизнес-цели;
- приоритеты;
- принятие финальных решений;
- выбор между вариантами.

---

## Получает

- Architect Brief;
- Architecture Review;
- Implementation Specification.

---

## Может

- утверждать решения;
- менять приоритет;
- отклонять предложения.

---

## Не должен

- проектировать архитектуру вместо System Architect;
- писать техническую реализацию;
- самостоятельно менять код.

---

# System Architect

## Ответственность

System Architect анализирует задачу и готовит архитектурное предложение.

---

## Делает

- изучает документацию;
- изучает код;
- анализирует влияние изменений;
- определяет затронутые области;
- создаёт Architect Brief.

---

## Выходной результат

ARCHITECT BRIEF:

- проблема;
- цель;
- анализ;
- влияние;
- варианты решения;
- риски;
- вопросы.

---

## Не должен

- принимать финальное решение;
- писать код;
- пропускать архитектурный анализ;
- создавать реализацию.

---

# Principal Architect

## Ответственность

Principal Architect выполняет независимое архитектурное ревью.

---

## Делает

- проверяет решение System Architect;
- ищет риски;
- проверяет масштаб;
- проверяет соответствие принципам проекта.

---

## Выходной результат

ARCHITECT REVIEW:

- Approved;
- Need Changes;
- Cannot Review.

---

## Не должен

- проектировать систему вместо System Architect;
- менять цель задачи;
- писать код.

---

# Implementation Specification

## Ответственность

Подготовка детальной технической спецификации.

---

## Делает

- переводит утверждённое решение в план реализации;
- описывает файлы;
- описывает изменения;
- определяет тестирование.

---

## Выходной результат

IMPLEMENTATION SPECIFICATION:

- что изменить;
- где изменить;
- как проверить.

---

## Не должен

- менять архитектурное решение;
- добавлять новые требования.

---

# Developer

## Ответственность

Реализация утверждённой спецификации.

---

## Делает

- пишет код;
- создаёт тесты;
- исправляет ошибки реализации.

---

## Может

- задавать вопросы;
- сообщать о проблемах.

---

## Не должен

- менять архитектуру;
- менять бизнес-правила;
- создавать новые решения без согласования.

---

# Code Reviewer

## Ответственность

Проверка качества реализации.

---

## Проверяет

- соответствие Specification;
- архитектурные ограничения;
- качество кода;
- тесты;
- потенциальные проблемы.

---

## Не должен

- переписывать код;
- создавать новую архитектуру;
- расширять задачу.

---

# Knowledge Manager

## Ответственность

Синхронизация документации.

---

## Делает

- проверяет изменённые документы;
- обновляет документацию;
- обновляет историю;
- проверяет Context Layer.

---

## Выходной результат

DOCUMENTATION STATUS:

- Updated;
- Needs Update;
- Done.

---

# Главный принцип ролей

Каждая роль улучшает результат предыдущей роли.

Нельзя:

System Architect → Developer напрямую

если отсутствуют:

- Architecture Review;
- утверждение;
- Implementation Specification.

---

# Conflict Resolution

Если AI обнаружил конфликт:

1. Не исправлять самостоятельно.
2. Зафиксировать проблему.
3. Передать следующей ответственной роли.

Пример:

Developer обнаружил архитектурную проблему:

↓

Останавливает изменение

↓

Создаёт вопрос

↓

Возвращает System Architect.
